**Greshake, Abdelnabi, Mishra, Endres, Holz & Fritz · 2023 · [arXiv:2302.12173](https://arxiv.org/abs/2302.12173)**

Every attack in the previous two entries assumes the attacker is the user. That is a manageable threat: the user is attacking a model they are already permitted to use, and the harm is bounded by what they could have found elsewhere. This paper points out that the interesting case is the opposite one, and it is the most consequential security result on the list.

**Indirect prompt injection.** The attacker does not talk to the model at all. They place instructions in **content the model will later retrieve** — a web page it browses, an email in the inbox it summarises, a document in the repository it searches, a review on a product page, a comment in a code file. An innocent user asks an innocent question. The application fetches the poisoned content, appends it to the context, and the model, which has no way to distinguish the developer's instructions from the user's from the attacker's, follows all three.

The failure is architectural and has a long lineage. **There is no separation between the control plane and the data plane.** Everything arrives as one flat sequence of tokens, and the model's only tool for deciding what is an instruction is that it looks like one. This is SQL injection, and cross-site scripting, and format-string vulnerabilities, arriving again in a system where the standard mitigation — parameterise the query, so data can never be parsed as code — has no analogue, because the model's entire capability rests on interpreting natural language and natural language is how instructions are expressed.

The paper's threat taxonomy is worth reading in full, because the imaginative work has been done for you: information exfiltration (the assistant reads your inbox and encodes the contents into a URL it fetches), fraud (it recommends the attacker's site), intrusion (it uses its own tool access to act), malware in the sense of injections that propagate to further systems, content manipulation, and denial of service. The authors demonstrated these against real deployed systems, not only against their own testbed.

> The model has no way to tell an instruction from a quotation, so any content it reads is potentially code, executed with the user's authority.

**What did not survive is nothing — this is the entry that has aged least and worries most.** Three years on, indirect prompt injection is unsolved, and the reason is that the fix everybody wants does not exist. Delimiters and spotlighting help and are bypassable. Instruction-hierarchy training reduces the rate and does not eliminate it. Classifier-based detection of injected content is an arms race against fluent text. Dual-model architectures, where a privileged planner never sees untrusted content and an unprivileged reader never holds capabilities, are the most principled direction — and they constrain what the system can do, which is exactly why they are unpopular. OWASP ranks prompt injection first among LLM application risks, and the honest position is that it is a property of the design rather than a bug in an implementation.

**The practical consequence is a design rule rather than a defence**, and it is the one I follow in my own [agent registry](/project/agents/): assume any content an agent reads may be adversarial, and let that assumption determine what the agent is permitted to *do*. Every tool an agent can call is recorded there with its effect — read-only, billed call, staged write requiring approval — because when injection is unpreventable, the only remaining control is the blast radius. An agent that can only read cannot be made to exfiltrate. An agent whose writes are staged for a human cannot be made to commit one. That is a weaker guarantee than anyone wants, and it is currently the strongest one available.
