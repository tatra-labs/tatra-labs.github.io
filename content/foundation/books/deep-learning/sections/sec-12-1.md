# 12.1 Large-Scale Deep Learning

Chapter 12 opens with the engineering, and the premise is stated bluntly: deep learning works because
individually simple units become intelligent in very large numbers, and getting to those numbers is a
systems problem.

## Making one machine fast

**CPU implementations** can be far faster than a naive version — the book cites fixed-point arithmetic
and careful use of vectorised instructions as sources of large gains — but the authors note that most
research groups moved past CPUs.

**GPUs** are the reason the field became practical. The argument the book gives is architectural rather
than incidental: graphics workloads are highly parallel, need high memory bandwidth, and tolerate low
branching and low clock speeds. Neural networks have the same profile. Every unit in a layer can be
computed independently of the others, and the operations are dense arithmetic on large buffers.

The book cautions that writing efficient GPU code is difficult, and recommends that most practitioners
should rely on libraries rather than implementing kernels themselves.

## Making many machines work together

**Data parallelism** splits the minibatch across machines, each computing gradients for its portion. It is
easy at inference and harder at training, because the parameters must be kept consistent. The book
describes **asynchronous SGD**, in which several cores read a shared parameter vector and write updates
without locking. Some updates are lost to races, and the reduction in the effective learning rate is more
than repaid by the throughput.

**Model parallelism** splits the model itself across machines, which is needed when a single model does
not fit.

## Making the model cheaper

**Model compression** replaces an expensive trained model with a smaller one that approximates it. The
book's framing is that a large model is often needed to *reduce variance* during training, and once
trained, its function can be reproduced by a smaller model — trained on data generated by the large one,
which can be sampled in unlimited quantity.

**Dynamic structure** avoids doing all the work on every input. A **cascade** runs a cheap detector first
and an expensive one only on the survivors; a **mixture of experts** uses a learned **gater** to route
each input to one of several specialised subnetworks. The book notes that dynamic structure interacts
badly with hardware: branching reduces parallelism, and the whole batch must take the same path to keep
the machine busy.

**Specialised hardware** is discussed with a note that reduced-precision arithmetic — the book mentions
implementations working with as few as 8 to 16 bits — is a viable direction.

## My take

Model compression as described here is **knowledge distillation** before that name existed. The insight
the book states — that the large model can generate unlimited training data for the small one — is
precisely why distillation works better than training the small model from scratch, and it is now how
essentially every deployed model is produced: a large teacher, a small student, the student trained on
the teacher's outputs.

The reduced-precision remark landed almost exactly. Training in 16-bit and inference in 8-bit or 4-bit are
now standard, and the whole economics of serving depends on it. What the section could not anticipate is
that the precision question would become a *format* question — that bfloat16 would beat float16 by
trading mantissa for exponent, and that the constraint would be dynamic range rather than bit count.

The mixture-of-experts discussion is the most interesting item to revisit, because the book identifies the
exact obstacle that had to be solved. Dynamic routing conflicts with parallel hardware, which wants every
element of a batch to follow the same path. Sparse mixture-of-experts models resolved this by routing
tokens rather than examples and by fixing the number of tokens each expert accepts, so the computation
stays dense in shape while being sparse in effect. The idea was here; what was missing was the trick that
makes it fit the machine.

Asynchronous SGD, by contrast, largely lost. Synchronous data-parallel training with an all-reduce won,
because gradient staleness costs more than synchronisation does once interconnects are fast.
